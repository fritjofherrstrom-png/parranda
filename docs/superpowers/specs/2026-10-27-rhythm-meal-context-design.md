Owner Codex, branch codex/rhythm-meal-context-20261027, base721c026a9d8fe591f14ffb0c315348ea1d6dc7a0. Public cf18a576 is unchanged during local work.

The user reports that Relaxed→Full leaves an edited day at four stops and explicitly approved time-aware lunch/dinner on27Oct. The native diagnosis proves old count retention:5→Remove4→Relaxed4→Full4 versus fresh Full6 through the actual built UI/HTTP/engine.

## Approach

Keep ordinary Remove/Replace, retry, priority adjustments and reload contracts. Only an explicit change of rhythm releases the old edit count/retained-set command. Keep removed identities in the existing absolute-date/place-scoped day-edit command, with a narrow release_extent flag for the changed rhythm; preserve Keep commitments separately and use the usual cancellation/Undo/persistence paths. The initial stable-ledger migration was rejected in independent review because it lost date scope. A same-rhythm tap remains a no-op. Keeping the old cap is the reproduced defect; clearing every choice would resurrect removed places and lose pins.

For meals, reuse the trusted server date/timezone and admitted preference fits, existing dayparts and geometry checks. Food priority can favour a lunch start around the existing local midday band, plus a separated evening meal in Full when remaining time and suitable distinct places permit it. Ranking remains content priority, not a universal visit-order rule. Reordering alone cannot make a dinner-only place a lunch candidate. Known closures, factual availability and final walking validation remain authoritative; unknown hours remain unknown. Café/fika requires the existing actual preference fit, not a new synonym or inferred menu.

The minimal extension threads private trusted meal context into existing bounded selection and ordering; it must not trust client clock/meal fields, acquire sources, force extra stops in scarce supply or expand distance budgets. Preserve explicit strict edits/pins/Live ordering constraints. Tomorrow and unknown timezone must not inherit today's lunch urgency. Any proposal labels are planning intent, never proof that a venue is open.

No source changes, provider loops, new integrations, city rules, automatic two-source requirement, new timeout, drag/drop or new paid/model calls. Each correction is independently traceable. New merge/deploy is not performed during local verification.
